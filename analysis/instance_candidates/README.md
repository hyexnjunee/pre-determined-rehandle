# 실험용 실데이터 후보 구간 (2026-10-13)

원본 CSV(동원 ARMG 2025-01~03)의 모든 블록 × 날짜 × 1시간 구간(44,258개)을 집계해,
"반출(GO) 트럭이 밀려 있고 GO rehandle 이 많고 SC 는 여유 있는" 구간을 골랐다.
웹 "실데이터 가져오기"에서 날짜 · 블록 · 시작 시각 · 60분으로 그대로 불러올 수 있다.

## 파일
| 파일 | 내용 |
|---|---|
| `hour_windows_all.csv` | 모든 1시간 구간의 지표 (아래 열 설명) |
| `candidates.csv` | 고른 구간 36개: A1 목표 12 · A2 목표 8 · B 대조 8 · C 대조 8 |
| `candidates_eval.csv` | 후보마다 비교군 MIP · 협업 MIP · 창 규칙 · 창 규칙(지원 끔)을 돌린 결과 |
| `scan.py` → `select.py` → `evaluate.py` | 위 세 파일을 만드는 스크립트 (웹 `app/realdata.py` 의 색인 · rehandle 복원을 그대로 사용) |

열: `n_go` `n_gi` `n_sc_main`(DS·LD) = 그 시간에 시작한 본 작업 수, `go_rh` = GO rehandle 개수(RH_CNT), `go_rh_jobs` = rehandle 있는 GO 수,
`go_wait_med_min` = GO 트럭 대기(완료 − 요청) 중앙값, `go_queued_at_start` = 구간 시작 전에 이미 요청한 GO 수,
`sc_busy` `lc_busy` = 그 시간 중 크레인이 무언가(AH·정리 포함) 하던 비율.

## 고른 기준
- **A 목표**: GO rehandle ≥ 4개 (rehandle 있는 GO ≥ 2), GO 대기 중앙값 ≥ 20분, 시작 때 기다리던 GO ≥ 1, SC 가동률 ≤ 0.35, LC 가동률 ≥ 0.8.
  조건을 만족하는 구간이 2,589개라 GO rehandle 많은 순으로, 블록당 2개 · 날짜당 1개까지 골랐다.
  A1 = SC 본 작업 2개 이상 (SC 도 자기 일이 있음), A2 = SC 본 작업 0~1개
- **B 대조 (둘 다 바쁨)**: A 와 같되 SC 가동률 ≥ 0.8, SC 본 작업 ≥ 6
- **C 대조 (평상시)**: GO rehandle 1~4개, GO 대기 중앙값 ≤ 12분, SC 가동률 0.3~0.6
- 공통: 본 작업 5~16개 (MIP 로 풀 수 있는 크기)

- 창 규칙은 A 에서만 크게 효과가 있고(9~19 %), SC 가 바쁜 B 에서는 거의 돕지 못한다(0.1 %). 평상시 C 는 2 % 수준.
- 협업 MIP 는 B 에서도 17 % 를 얻는다: SC 자기 트럭을 기다리게 하면서 돕는 해. 규칙(자기 트럭이 오면 멈춤)과 MIP 의 차이가 여기서 드러난다.
- **주의 1**: 이 실행 환경의 Gurobi 는 크기 제한 라이선스라 큰 구간의 협업 MIP 는 풀지 못했다 (괄호 안 숫자가 푼 개수).
  맥북에서 `python evaluate.py ...` 또는 `web/experiments/run_experiments.py --groups real` 로 다시 돌리면 전부 채워진다.
- **주의 2**: `sc_busy` 는 실제 기록 기준이라 AH·선반출 준비 같은 정리 작업을 포함한다. 모델에는 본 작업(DS·LD)만 들어가므로,
  모델 안의 SC 는 실제보다 한가하다. B 를 "SC 본 작업 ≥ 6" 으로도 거른 이유.
