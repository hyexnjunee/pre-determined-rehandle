## 1. 왜 고쳤나
발표자료 수리모형 고민 ②. 원본은 두 제약 때문에 지원받는 동안 원래 크레인이 다음 작업으로 넘어가지 못한다.
- (5) 같은 크레인의 연속 본 작업은 순서 고정: $s_j + p_j + t_{jk} \le s_k$
- (11) rehandle 은 누가 하든 본 작업보다 먼저: $s_r + p_r \le s_{j(r)}$

그래서 반대편 크레인의 rehandle 이 늦으면 원래 크레인은 $j$ 앞($b+\delta$)에서, 다음 작업의 트럭은 TP 에서 기다린다.
적하 ↔ 양하, 반입 ↔ 반출, 외부트럭끼리는 흐름이 달라 바꿀 수 있는 경우가 많다 (모형의 한계).
흐름이 다른 이웃 한 쌍만 풀어 주는 것보다 경우가 많으므로 **K칸 안이면 모두** 바꿀 수 있게 했다.
처음(11-06)에는 적하끼리를 선박 적재 순서라며 고정했으나, 경우에 따라 적하끼리 바꾸는 편이 더 좋을 수 있어
(아래 4절: 8개 중 3개에서 더 좋아짐) **기본은 고정 없음**으로 바꿨다. 선박 적재 순서를 꼭 지켜야 하는 실험만 `SWAP_FIXED_TYPES = ("LD",)`.

### 성질
- **K = 0 이면 원본과 같은 식**: $S = \emptyset$, $P^{fix}$ = 연속 쌍, (11') = 직전 작업 하나 → 같은 목적값 (노트북 toy · 생성 인스턴스 3개 테스트)
- **K 를 늘리면 같거나 좋아짐**: 허용 집합이 커지기만 한다 (toy, truck_wait: K 0 → 1 → 2 → 3 = 1,047 → 884 → 757 → 723)
- **이동 범위**: 한 작업은 $K$ 칸 안의 작업과만 순서가 바뀌므로 실제 위치는 원래 위치 ± K.
  그래서 실제 순서에서 이웃할 수 있는 쌍은 원래 거리 $\le 2K+1$ 뿐 → 그 안의 쌍에만 (5a)(5b) 를 두면 충분하다
  (이웃이 아닌 쌍의 겹침은 이웃 쌍 사슬로 막힌다. 처리시간 > 0 이라 순환도 생기지 않는다)
- $F$ 유형끼리는 $K$ 칸 안이어도 고정 → `("LD",)` 이면 선박 적재 순서 보존 (테스트에서 확인). $F$ 를 비우면 허용 집합이 커지기만 하므로 같거나 좋아짐
- 크기: 쌍 수가 크레인당 약 $n(2K+1)$ 로, 변수 $w$ 는 $nK$ 개 정도. toy 806 → 823 변수 (K=2)

## 3. 웹 · 실험
- 어댑터 `web/app/methods/coop_swap.py` (`CoopSwap`, 협업 어댑터를 상속): 옵션 `swap_window`(K), `swap_fixed_ld`(적하끼리 고정, **기본 끔**), `swap_fixed_ds`(양하끼리도 고정, 기본 끔).
  결과 지표: `n_swaps`(바꾼 쌍), `n_swaps_ld`(그중 적하끼리), `swaps_by_type`(유형 쌍별), `swapped_pairs`, `moved_jobs`, `max_shift`, `swap_pairs`(바꿀 수 있는 쌍)
- **교환만** (지원 없이 순서만) = 같은 방법에서 `allow_assist = False` → 실험 키 `full_swaponly`.
  비교군 → 교환만 → 협업 → 협업 + 교환 으로 효과를 나눠 볼 수 있다
- **롤링판** `rolling_coop_swap`: 재계획마다 공개된 작업 안에서 K칸 교환. 재계획마다 다시 바꾸므로 **누적 이동은 K 보다 클 수 있다**
  → 최종 검사는 "고정 유형끼리 원래 순서" 만 확인하고 (기본은 고정 없음), 최종 순서에서 뒤바뀐 쌍 수 · 그중 적하끼리 · 최대 이동 칸 수를 기록
- 독립 검사 `rules.verify(..., swap={"fixed": F, "window": K})`: 본 작업이 같은 집합인지, 고정 유형끼리 뒤바뀌지 않았는지,
  뒤바뀐 쌍의 원래 거리 ≤ K 인지, `HOME_RH_FIXED` 를 실제 순서의 직전 작업 기준으로 검사
- 실험: `python experiments/run_rolling.py --set real2026_3h --mip-only --swap --swap-window 2 ...` (적하끼리 고정 비교는 `--swap-fixed-ld` 를 붙여 한 번 더)

## 5. 주의 · 남은 것
- **현장 허용 여부**: 트럭을 도착 순서와 다르게 처리하는 것(비 FCFS)이 운영상 허용되는지, 적하 · 양하 AGV 끼리 순서를 바꿔도 되는지 확인 필요.
  안 되면 `swap_fixed_ld` · `swap_fixed_ds` 로 그 유형끼리 고정하거나 K 를 줄인다 (실험은 고정 없음 · 적하 고정 두 가지로 돌려 차이를 보면 됨)
- **공정성**: 목적이 대기 합이라 짧은 작업 · 일찍 끝나는 작업을 앞당기는 쪽으로 간다. 트럭 하나의 최대 대기가 늘 수 있음 → 최대 대기 지표를 함께 볼 것
- **롤링의 근시안 (보완 ver 만의 문제 아님)**: 재계획 시점에 아는 작업만으로는 rehandle 을 언제 해도 목적값이 같은 경우가 많다(동점).
  이때 늦게 하는 해를 고르면 나중에 온 외부트럭과 엉킬 수 있다 (작은 예에서 롤링 협업 257 vs 같은 문제를 보완 ver 로 476, 교환은 0개).
  개선 후보: 동점이면 rehandle 을 일찍 하도록 아주 작은 가중치 ($\varepsilon \sum_r s_r$) — 원본 · 보완 ver 둘 다에 해당
- 크기 제한 Gurobi(컨테이너)에서는 작은 인스턴스만 확인. 실데이터 세트(real2026) 비교는 연구실 서버에서
