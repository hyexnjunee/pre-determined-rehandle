## 원본 대비 변경 요약
- 본 작업(DS/LD/GI/GO)의 할당과 크레인 내 순서를 고정 (DS·LD → SC, GI·GO → LC, 순서는 입력 dict 순서)
- 의사결정은 Rehandle 할당 x_rv (LD·GO에 딸린 rehandle)
- 본 작업끼리의 순서 변수 y 제거 → 연속 본 작업 고정 순서 제약 (5)
- Rehandle이 포함된 쌍에만 y_ij (크레인 인덱스 없음, M(3 - y - X - X) 형태)
- 크레인 간 간섭 순서 z 와 ETD 제약은 유지
- 해측 TP = Bay 0, 육측 TP = Bay N+1
- 옵션: ALLOW_ASSIST (False = Baseline), HOME_RH_FIXED, OBJ, RH_AFTER_ARRIVAL (True 면 rehandle 은 그 본 작업 트럭 도착 뒤: $a_r = a_{\pi(r)}$, 노트북 기본 False · 웹 기본 True), LD_LOOKAHEAD (적하 rehandle 은 AGV 도착 H 초 전부터: $a_r=\max(0,a_{\pi(r)}-H)$, 기본 None), CRANE_READY (크레인이 비는 시각 $\text{ready}_v$: 첫 이동 $\tau^0_{vi}=\text{ready}_v+|L_v-o_i|\hat t$, 기본 0 · 롤링 호라이즌용)

## 목적함수
- OBJ = "makespan" / "truck_wait" (모든 트럭) / "go_wait" (GO 트럭만)
- 트럭 대기 W_j = 트럭 출발 − 도착 a_j. DS·GI 는 시작 + pick, LD·GO 는 완료 시각에 트럭 출발
- a 는 목적함수에서 상수 → 스케줄에는 제약 a ≤ s 로만 영향 (트럭이 늦게 와서 크레인이 기다릴 때만 binding)

## 트럭 도착 시각 a 를 정하는 방법
- 인스턴스 편집기에서 작업마다 직접 입력 (비우면 default_ready)
- 무작위 생성기: 크레인 순서를 따라 등간격. SC 의 k 번째 작업(0부터) a = k × SC 간격, LC 의 k 번째 작업 a = k × LC 간격
  - 트럭은 크레인이 처리할 순서대로 도착한다고 가정 (predetermined sequence 와 일관)
  - 간격 < 크레인 1작업 평균 시간이면 트럭이 이미 와서 기다리는 상황 → 제약이 거의 안 걸리고 대기 값만 커짐
  - 간격 > 크레인 1작업 평균 시간이면 크레인이 트럭을 기다리는 상황 → 제약이 걸려 스케줄이 바뀌고, 그 빈 시간에 반대편 지원 여지가 생김
  - toy 기준 (makespan 목적): LC 간격 0~30 은 스케줄 동일, 60 부터 크레인이 트럭을 기다림
  - 간격은 소수도 가능 (예: 0.5, 0.25). 편집기의 a 칸도 소수 입력 가능

## 휴리스틱: Window–Slack 지원 규칙 (웹 `window_rule`, 2026-10-13)
`web/app/methods/window_rule.py`. `analysis/assist_cases/assist_rules.html` 의 규칙을 옮긴 solver-free 방법.
- 규칙 0: rehandle 은 트럭 도착 뒤 (옵션, 기본 켬) · 규칙 1: 원래 크레인이 바쁠 때만 ($a_j < A_H$)
- 규칙 2: 시작 시각은 노트북 ETD 식으로 계산 (디코더) · 규칙 3·4: 위 rehandle 부터 하나씩 넘기고, 지원 크레인 자기 트럭이 rehandle 시작 전에 와 있거나 본 작업이 빨라지지 않으면 멈춤. 개수 상한 없음
- 규칙 5(내려놓는 bay 변경)는 MIP 와 다른 문제가 되어 넣지 않음. 선택: 목적값 보호(규칙 밖, 기본 끔)
- 디코더: 두 크레인 머리 작업이 간섭할 때 두 순서를 끝까지 계산해 보고 고름(rollout). 탐욕만 쓰면 무지원 스케줄부터 MIP 보다 크게 나빠짐 (탐욕 디코더의 무지원 스케줄이 비교군 MIP 보다 최대 61 % 나빴음 → rollout 후 소형 12개 중 7개가 비교군 MIP 와 같은 값)
- 결과에 판단 기록(본 작업별 지원 개수 · 멈춘 이유)과 지원 효과 지표를 남김

### 적하 rehandle 사전 정보 (LD_LOOKAHEAD, 2026-10-28)
연구 고민 노트: "적하쪽 리핸들은 AGV 가 도착하는 시점을 안다고 가정하고 반출 리핸들은 ET(외부트럭)이 도착하는 시점을 모른다는 가정" — 선행연구 Park et al.(2010, OR Spectrum 32, 류광열 교수님 연구실) 참고.
- 적하(LD): AGV·내부트럭 도착을 H 전부터 앎 → $a_r=\max(0,a_{\pi(r)}-H)$ (노트북 `LD_LOOKAHEAD`, 웹 "적하 rehandle 은 AGV 도착 H분 전부터", 기본 끔 · H 30분)
- 반출(GO): 외부트럭 도착을 모름 → 도착 뒤에만 (`RH_AFTER_ARRIVAL`, 1단계). MIP 는 미래 도착을 아는 상태로 계획하므로 상한. 2단계 = 아래 롤링 호라이즌
- 비교군은 rehandle 이 본 작업 안이라 미리 할 수 없음 (현재 운영 방식). 협업 MIP · 창 규칙 v1/v2 에 같은 옵션, 조건이 다르면 "MIP 대비" 계산 안 함
- 동원 데이터는 LD rehandle 3.5 % 로 드물어 실험용 생성기 프리셋 "적하 rehandle 실험값" 추가 (LD 6 · DS 4, LD RH 확률 0.5, SC 간격 400 s)
- 창 규칙 v2, seed 1000~1024 (지원 끈 경우 대비): 지원만 4.6 % → 지원 + AGV 30분 사전 정보 15.6 % (사전 정보만, 지원 없이 5.9 %). LD rehandle 지원 24 → 81 / 128개
- 소형(LD 4·DS 2·GI 2·GO 2, 6개) 협업 MIP: 도착 뒤 → 30분 사전 정보로 0 ~ 34 % 감소, 창 규칙 v2 해를 MIP 에 고정해도 모두 실행 가능

### 롤링 호라이즌 (2026-10-28, 웹 "롤링 · …", `web/app/methods/rolling.py`, `web/experiments/run_rolling.py`)
연구 고민 노트: "적하 리핸들은 AGV 도착을 알기 때문에 BTB 로 간주 → 롤링 호라이즌으로 실험해야 의미. 육측 리핸들은 외부트럭이 도착해야, AGV 정보는 1시간 전에."
- 정보 공개: 외부트럭(GI·GO) = 도착 순간 (반출 RH 도 도착 뒤), AGV(DS·LD) = 도착 H분 전 (기본 60, 적하 RH 는 $a-H$ 부터)
- 재계획(작업 투입): 새 정보 시점마다, 또는 일정 간격 (웹 옵션 "작업 투입 방식 = 일정 간격", 첫 작업 시각부터 Δ분마다 · 기본 30분, 그 사이 정보가 들어온 작업은 다음 시점에 한꺼번에 투입; `run_rolling.py --replan event,15,30,60`). 크레인별로 앞에서부터 공개된 작업까지만 넣은 부분 문제 (순서 고정이라 그 뒤는 어차피 못 함).

#### 5시간 실험 세트 (`rolling5h`, 2026-10-28)
- 트럭 도착을 5시간(18,000 s) 안에 고르게: 크레인별 작업 수 = ⌊T / 간격⌋, 간격 = 작업 1개 평균 작업량(SC 310 s · LC 380 s) / 목표 부하 ρ

#### 10시간 실험 세트 (`rolling10h`, 2026-10-30)
- 시간 창 10시간(36,000 s). 균형 18개 = SC ρ × LC ρ {0.5, 0.7, 0.9}² × 시드 2 (도착 고르게, 작업 105~189개)

  누적 도착률의 (k + u)/n 분위점(u ~ U(0.2, 0.8))에 k번째 트럭 → 크레인 순서 유지, 몰린 칸은 간격이 좁음

  · SC만(3~6h, LC 고르게) · LC만 · 엇갈린(SC 2~4h, LC 6~8h) · 동시(4~6h 둘 다) · 점점 증가(0.3 → 1.7배)

## 남은 과제
- **롤링 실험**: 창 규칙에 지원 시점 창 추가 (H 가 클 때 너무 일찍 돕는 문제), Mac 에서 롤링 협업 MIP · 정적 협업 MIP 로 상한 비교 (`python experiments/run_rolling.py --mip`), 외부트럭 사전 정보(게이트 통과 시점) 민감도
- **창 규칙 처리 순서**: 지금은 무지원 스케줄에서 먼저 시작하는 GO 부터 지원을 정함. 빈틈을 rehandle 많은 GO 나 효과 큰 GO 에 먼저 주거나, 넣은 뒤 다른 GO 와 바꿔 보는 개선 필요 (1013 - 02 의 GO_5 ↔ GO_7)
- **비교군과 협업(지원 없음)의 차이**: rehandle 을 본 작업에 합친 비교군과 분리한 협업 모델은 ETD 계산이 달라, `RH_AFTER_ARRIVAL=True` · 지원 없음이어도 값이 조금 다를 수 있음 (예: 웹 생성 인스턴스 2965.5 vs 2991.0)
- **제한적 순서 교환**: 지원받는 동안 원래 크레인이 다음 작업(트럭 도착)을 먼저 하도록 한 칸 교환 허용할지 (연구 고민 노트)
- **대기열 인스턴스**: 웹 생성기에 "대기열 있는 보정값"(SC 584 / LC 200 s, GO 대기 중앙값 13.5분) 추가. 실제 19분과 맞추는 보정은 남음
- Seaside 다음 본 작업 no-delay 제약
- 지원 시 rehandle 목적 Bay 재결정
- 안전 여유 현장 값 확정
- TP 작업 유형별 처리시간 (GI·GO 가 더 오래 걸림) 반영 여부
